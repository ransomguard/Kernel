# RansomGuard v0.3.1 — Verification (커널 방어 기능 검증)

새 방어 기능을 추가하는 버전이 아니라, **기존 커널 방어 기능이 실제 환경에서
동작함을 검증**하고, 검증에 필요한 **테스트 클라이언트 옵션을 확장**한 버전입니다.

**변경일:** 2026-09-22
**이전 버전:** `v0.3.0_minifilter`

> **커널 코드 변경 없음.** 이번 버전에서 드라이버(`.sys`) 소스는 수정하지
> 않았습니다. 방어 로직은 이미 v0.2.0/v0.3.0에 구현되어 있었고, 이번 작업은
> 그 로직을 VM에서 실제로 켜서 동작을 확인하고, 확인에 필요한 도구를 보강한 것입니다.

---

## 이번 버전의 목적

WBS 상 "구현됨"으로만 표시되어 있던 커널 방어 항목들을, VM에서 실제로 동작시켜
**"검증 완료"** 상태로 끌어올렸습니다. 표에만 적힌 기능이 아니라 실측으로
동작을 증명하는 것이 목표입니다.

| WBS | 항목 | 이전 | 검증 후 |
|---|---|---|---|
| 3.2.5 | 프로세스 생성 콜백 + 커맨드라인 파싱 | 70% | **100% 완료** |
| 3.2.6 | vssadmin/wbadmin 패스트패스 (+ AUDIT/BLOCK) | 75% | **100% 완료** |
| 3.2.7 | ObRegisterCallbacks 자기보호 (SelfProtect) | 80% | **100% 완료** |
| 3.2.8 | IPC 기반 PID 종료요청 핸들러 | 90% | **100% 완료** |

## 테스트 클라이언트 확장 (유일한 코드 변경)

`Anti_Ransom_TestClient`에 검증용 커맨드라인 옵션을 추가했습니다.

| 옵션 | 용도 |
|---|---|
| `--terminate <PID>` | `IOCTL_RG_TERMINATE_PROCESS`로 특정 PID 종료 요청 (3.2.8 검증) |
| `--policy audit` / `--policy block` | FastPathMode를 AUDIT/BLOCK으로 전환 전송 (3.2.6 검증) |
| `--keep-selfprotect` | 정책 전송 시 SelfProtect를 강제로 끄지 않음 (3.2.7 검증) |

> `--keep-selfprotect`가 필요했던 이유: 기존 클라이언트는 정책 업데이트 시
> `EnableSelfProtect=0`을 항상 전송해, 레지스트리로 SelfProtect를 켜도 클라이언트
> 실행 순간 다시 꺼졌습니다. SelfProtect 자기방어를 검증하려면 클라이언트가
> 이를 끄지 않아야 하므로 옵션으로 분리했습니다.

## 검증 결과

VMware Win11 (26100), testsigning on. 기존 드라이버 서비스명 `ARWDrv`.

### 3.2.5 / 3.2.6 — 패스트패스 탐지·차단 + 커맨드라인 파싱

| 시나리오 | 관찰 | 결과 |
|---|---|---|
| BLOCK 모드에서 `vssadmin delete shadows /all /quiet` | RULE 1001 HIT, 커맨드라인 정확히 파싱, "액세스 거부"로 실행 차단 | 통과 |
| AUDIT 모드에서 동일 명령 | RULE 1001 HIT은 뜨되 차단하지 않음(탐지만) | 통과 |

> **AUDIT vs BLOCK 대비**가 핵심입니다. 같은 규칙·같은 명령이 모드에 따라
> "탐지만" / "탐지+차단"으로 갈립니다 — AUDIT로 오탐률을 먼저 관찰한 뒤
> BLOCK으로 전환하는 단계적 배포 전략을 실증합니다.

### 3.2.8 — PID 종료 요청 + 임계 프로세스 보호

| 시나리오 | 관찰 | 결과 |
|---|---|---|
| 일반 프로세스(메모장 등) 종료 요청 | 정상 종료, ResultStatus 성공 | 통과 |
| 임계 프로세스(csrss) 종료 요청 | 커널이 거부, `STATUS_ACCESS_DENIED (0xC0000022)` | 보호 |

> 엔진이 무엇을 지시하든, 커널이 임계 프로세스 화이트리스트로 최종 거부합니다
> ("커널은 유저 모드의 판단을 신뢰하지 않는다"). csrss를 종료하면
> `CRITICAL_PROCESS_DIED`로 시스템이 다운되므로, 이 거부가 fail-safe입니다.

### 3.2.7 — SelfProtect 자기방어 + 킬 스위치

레지스트리 킬 스위치로 활성화/해제를 통제합니다:
`HKLM\SYSTEM\CurrentControlSet\Services\ARWDrv\Parameters\EnableSelfProtect`

| 상태 | SelfProtectEnabled | 엔진 프로세스 taskkill | 결과 |
|---|---|---|---|
| **켜짐** (EnableSelfProtect=1) | 1 | `액세스 거부` | 자기방어 |
| **꺼짐** (킬 스위치 0) | 0 | 종료 성공 | 킬 스위치 |

> "켜짐=거부 / 꺼짐=성공"의 대비가 검증의 핵심입니다. 자기방어가 동작하는 것뿐
> 아니라, **킬 스위치로 개발자가 안전하게 빠져나올 수 있음**까지 확인했습니다.
> 검증 중 엔진 프로세스 강제 종료 시 자동 등록 해제(`ArwEvtFileCleanup`)가
> 동작하는 것도 함께 확인되었습니다.

## 검증 절차 요점

- 기존 드라이버(`ARWDrv`)는 `sc start`, 미니필터(`Anti_Ransom_FsFilter`)는 `fltmc load`로 로드.
- 두 드라이버는 altitude/디바이스 이름이 겹치지 않아 동시 로드 가능(데모 완성형).
- SelfProtect 활성화는 레지스트리 값 변경 후 **드라이버 재시작 시점에 반영**됨.
  값을 바꿔도 재시작 전에는 이전 상태로 동작하므로, `sc stop ARWDrv` →
  `sc start ARWDrv` 순서를 지킬 것.
- 검증 전 **VM 스냅샷**을 확보한 뒤 SelfProtect를 켤 것. 킬 스위치 검증 완료 전까지는
  자기 자신이 잠길 위험이 있음.

## 현재 상태

- 혼자 검증 가능한 커널 방어 항목(3.2.5/6/7/8)이 전부 **100% 완료**.
- SelfProtect는 현재 **꺼진 상태(EnableSelfProtect=0)**로 두어 개발 편의 확보.
  발표 시에만 레지스트리 값을 1로 켜 자기방어를 시연.
